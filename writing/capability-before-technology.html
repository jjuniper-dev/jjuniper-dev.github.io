Capability before technology.

October 2026

A requirement that names a product is not a requirement. It is a decision someone has already made, wearing a requirement's clothes.

"We need containerization." "We need a vector database." "We need Copilot for this." Each of these sounds specific, and each hides the question that matters: what does the system have to be able to do? Containers are one way to deploy an application. A vector store is one way to retrieve by meaning. Neither is the need.

The order I try to keep

Business need, then capability, then constraints, then architecture, then platform, then technology. Going left to right, the options narrow. Going right to left, you get a technology that is looking for a justification, and the justification usually turns up.

Naming the function first has a practical payoff. "Runtime and application deployment" can be satisfied by several things, including something that already exists and that nobody on the project had thought to ask about. "Containerization" can only be satisfied by containers.

Existing technology is evidence, not the requirement

None of this means ignoring what is already built. A working prototype is the best evidence you will get about what the need really looks like. The mistake is to let it stand in for the need. Read it as a data point: here is one thing that worked, here is what it assumed, here is what it cost.

The same goes in the other direction. Validating a choice because it is already in place is as much a shortcut as rejecting it because it is not fashionable.

A test you can run in a meeting

When someone states a requirement, ask whether you can write it without any product name or vendor term. If you cannot, you are probably looking at a solution. Ask what it is for, and write that down instead.

This is a personal note. It reflects my own working habits, not the position of any organization I work with.
